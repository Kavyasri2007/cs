Module 4: Cross-Site Request Forgery (CSRF)

Variant: GET-based Forged Action

Demonstrating how an untrusted third-party site abuses the victim's ambient authenticated browser session to trigger unauthorized state-changing operations without user intent.

1. Concept & Security Impact

Cross-Site Request Forgery (CSRF) is a confused deputy attack where a malicious website causes a user's web browser to perform an unwanted action on a trusted site where the user is currently authenticated.

Why Authentication Alone Fails: Browsers automatically attach stored credentials (session cookies) to cross-origin HTTP requests. The receiving server verifies the valid session cookie and confirms who the user is, but has no intrinsic way to verify intent—i.e., whether the user intentionally initiated the request.

Harmless Educational Setting: To demonstrate CSRF safely, this lab modifies an educational profile setting (status message / notification preference) for the seeded dummy student account alice. No real-world financial, password, or sensitive actions are utilized.

9 & 10. Viva Preparation: Questions, Answers & Alternative Mitigations

Q1: Why does authenticated session alone not prove user intent?

Answer: Web browsers operate on an ambient credential model: whenever an HTTP request is made to a domain, the browser automatically attaches all cookies stored for that domain. The server receives the cookie and can verify identity ("This is Alice's session"), but cannot discern whether the request was generated by Alice intentionally clicking a button on the real site, or silently forged by malicious JavaScript on an external third-party site.

Q2: How does the SameSite cookie attribute behave (Lax vs Strict vs None)?

Answer: The SameSite attribute directs the browser when to send cookies with cross-site requests:

  • SameSite=Strict: The cookie is never sent in cross-site requests, even when following a regular link from an external site. Provides maximum CSRF protection, but degrades user experience when following external links.
  • SameSite=Lax (Modern Browser Default): Withholds cookies on cross-site subresource requests (e.g. <img>, <iframe>, fetch()), BUT sends cookies on top-level cross-site GET navigations (e.g. clicking a link <a href>). This is why state-changing GET endpoints remain dangerously vulnerable to CSRF even in modern browsers!
  • SameSite=None: Cookies are sent in all cross-site contexts (requires the Secure HTTPS flag in modern browsers).
Q3: How does the Synchronizer Token Pattern work?

Answer: When a user begins a session, the server generates a cryptographically random, unguessable secret token and stores it in the server-side session. When rendering forms, the server embeds this token into a hidden input field. Upon form submission, the server compares the submitted token against the stored session token using constant-time string comparison (hmac.compare_digest). Because the browser's Same-Origin Policy (SOP) prevents external origins from reading DOM content on the target site, an attacker cannot retrieve or guess the token.
