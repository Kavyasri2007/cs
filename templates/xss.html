Module 3: Reflected Cross-Site Scripting (XSS)

Variant: Reflected XSS via Search Query

Demonstrating how reflecting unsanitized and unencoded user input into an HTML response leads the browser to interpret data as executable client-side JavaScript.

Note on Ethical & Academic Guidelines: In strict compliance with assignment instructions, this demonstration uses harmless alert and DOM indicators. No document.cookie extraction or session theft payloads are included.

1. Concept & Security Impact

Cross-Site Scripting (XSS) occurs when an application receives untrusted data and includes it in a web page sent to the browser without proper validation or context-aware encoding.

Reflected XSS: In reflected XSS, the injected payload is part of the immediate request (e.g. search query parameters in the URL) and is reflected back by the server in the immediate response. When the victim clicks an attacker-crafted link, their browser executes the script within the trust boundary of the vulnerable application.

Impact: Attackers can manipulate page content (defacement), redirect users to malicious clones, capture keystrokes, or issue unauthorized requests from the user's browser.

9 & 10. Viva Preparation: Questions, Answers & Alternative Mitigations

Q1: What are the three primary types of XSS (Stored, Reflected, DOM-based)?
  • Reflected XSS: The payload is delivered via the request (e.g. query string) and reflected immediately in the server's HTTP response. Requires victim to click a malicious link.
  • Stored (Persistent) XSS: The malicious payload is saved permanently in a datastore (e.g. database comment, forum post) and delivered to all users who subsequently view the stored data.
  • DOM-based XSS: The vulnerability exists entirely on the client side; client JavaScript reads data from a source (e.g. location.search) and writes it unsafely to a dangerous sink (e.g. element.innerHTML, eval()) without server roundtrip.
Q2: Why does context-aware output encoding matter?

Answer: Different locations in an HTML document parse data using different state machines. HTML body encoding (< to &lt;) is effective between HTML tags, but if untrusted input is placed inside an attribute (e.g. <input value="USER_INPUT">) or a JavaScript block (e.g. <script>var name = "USER_INPUT";</script>), standard HTML escaping is insufficient. Context-aware encoding ensures data is escaped according to the specific grammar of the target sink (HTML Body, Attribute, JavaScript, CSS, or URL).

Q3: What are the exact capabilities and limitations of HttpOnly cookies?

Answer: Setting HttpOnly on session cookies instructs the browser that the cookie must not be accessible via client-side scripts (document.cookie).

Crucial Viva Clarification: HttpOnly mitigates session hijacking via cookie theft, but does NOT prevent XSS itself. Even with HttpOnly enabled, injected JavaScript can still perform arbitrary actions: deface the page, log keystrokes, capture form inputs, or send authenticated HTTP requests (XHR/fetch) using ambient session credentials!
Q4: What role does Content Security Policy (CSP) play?

Answer: Content Security Policy (CSP) is an HTTP header (e.g. Content-Security-Policy: default-src 'self') that restricts the resources (scripts, images, stylesheets) the browser is allowed to load and execute. By disabling inline scripts (disallowing 'unsafe-inline') and requiring cryptographic nonces or hashes for approved scripts, CSP acts as a robust second line of defense against XSS.
